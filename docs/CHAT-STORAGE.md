# Private chat attachments

New chat attachments use the private Supabase bucket `whisper-chat-files`. The browser still encrypts bytes with AES-GCM using the room key and `file` AAD before sending. The gateway/Edge Function handles ciphertext only; plaintext filenames/type/size remain inside encrypted message content. No additional frontend library, login or public/signed download URL is introduced.

## Lifecycle

1. The signed gateway validates the request. A privileged RPC authorizes the live room/member, checks budgets and reserves an opaque random object path before any upload.
2. Edge uploads the binary ciphertext through the Storage API with a server-only service key. The DB receives an `@storage/<opaque-id>` reference and IV instead of the large base64 payload. An existing committed nonce returns its original sequence without re-uploading.
3. Downloads authorize the member and message again, fetch the private object on the server, and return ciphertext with no-store headers. The browser decrypts and validates the actual file before saving it. Existing inline DB attachments remain readable and naturally expire with their rooms; they are not bulk migrated.
4. Every minute, Supabase Cron invokes the cleanup endpoint via pg_net with a random token generated and kept in database Vault. Cleanup leases up to 100 obsolete uploads, deletes actual objects using the Storage API, and acknowledges metadata only on success. Removing only SQL storage metadata would leave physical objects behind, so that is deliberately not used.

Deleted messages, rolling-window eviction, destroyed rooms, host departure and expired rooms make committed objects eligible for the next cleanup run. Expiry independently denies downloads even if physical cleanup is delayed. Failed deletion keeps its metadata for retry after one minute. Uploads that never commit get ten minutes to finish before cleanup, exceeding the bounded network upload timeout. Active referenced objects are never selected. Storage outages can delay physical removal; this is not a promise of immediate or forensic erasure, including provider backups.

## Limits and permissions

- Original allowlist unchanged: PNG/JPEG/WebP, PDF, TXT/CSV; 256 KiB plaintext maximum per attachment, 262,160 bytes including the GCM tag in Storage.
- Existing 2 MiB room budget includes binary uploads and pending reservations. At most four pending reservations per room, plus upload/room/network rate limits. Storage capacity is not a user upload allowance.
- Bucket is private with octet-stream only and a restrictive policy excluding anonymous/authenticated browser roles. Only the server service role uploads/reads/deletes; the key never enters browser responses.
- Reservation metadata has RLS and no browser-role access. It contains random path, room/member hash/nonce, ciphertext digest, byte length, IV and lifecycle state, not plaintext content.

## Deployment

Apply `20261113070000_chat_file_storage.sql`, then deploy the updated Edge function. The existing deployment script sets only the public cleanup URL in Vault and verifies the fourth cleanup job is active. The cleanup token is generated by the migration inside Vault and is not a new GitHub Actions secret. Existing three jobs are preserved. No Vercel UI change is required for this storage flow.

## Local verification

Local bridge uses a disposable filesystem object store behind the same production orchestration, not a production bucket. PostgreSQL integration runs the actual reservation/authorization/cleanup SQL; only the platform Vault secret source is emulated. Tests cover ciphertext roundtrip, old DB attachments, outsiders, nonce retry, quota/abandoned uploads, deletion/rolling/destruction/expiry, leases and Storage outage retries. Browser tests upload and download TXT/PNG/CSV through actual UI and check the DB contains an opaque reference, not file contents. REST adapter unit tests cover authenticated download, no public URL/upsert, size bounds and batch removal.

Local tests do not establish that live bucket/Vault/pg_net permissions or the scheduled callback work in the hosted project. Those require an approved backend deployment and a live upload/delete/cron smoke check. This change has not been deployed.

Verified locally on 2026-11-13: 61/61 unit tests, 44/44 Edge API tests (20 chat cases), three targeted browser cases, frontend typecheck, separate TypeScript check of the Edge entrypoint using a Deno global declaration, production build and whitespace checks. Attachment screenshots were inspected at mobile width. The temporary database was removed after QC.
