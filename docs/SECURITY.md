# Security model

## What is protected

For new compact links, the browser generates a fresh random 128-bit seed, encoded as 22 canonical base64url characters in `/#<seed>`. HKDF-SHA256 with salt `hush:short:v1` and distinct `encryption`, `access` and `lookup` info labels derives three 256-bit outputs. **The effective secret strength is 128 bits**, not 256. A random 96-bit AES-GCM IV is still generated per encryption. Legacy links use a random 256-bit AES key and remain readable. Authentication tag verification fails closed on a modified ciphertext/IV/key. Fixed `hush:message:v1` associated data separates this protocol from other uses. New links keep the seed in the fragment; legacy links keep `#k=…&a=…` there. Browsers do not send fragments in HTTP requests. New-link AES key and access capability are derived locally; the seed and AES key are never uploaded. The derived access capability is sent when creating the ciphertext record and in the explicit open POST body. The lookup ID is supplied on create, validated and inserted with collision refusal, never an upsert/overwrite. Database rows contain its SHA-256 hash, not the capability. The sender has a separately generated random revocation capability whose hash is stored; it is deliberately not derived from the recipient seed.

A six-digit code is an additional server-side gate, not the encryption key. Codes use cryptographic randomness with rejection sampling; HMAC-SHA256 with a server-only pepper and per-message ID protects the stored code. The code travels in POST JSON over HTTPS; it must never be logged. Only a caller already holding the 256-bit access capability can consume a code attempt. Five nonempty wrong attempts invalidate and delete the row. Missing code does not count; valid timed reads do not reset the wrong-attempt budget.

Open/revoke tokens and PINs are never accepted in URL query parameters. Open tokens cannot revoke a message. Plaintext is rendered with `textContent`. Optional rich markup is sanitized with locally vendored DOMPurify both before encryption and after decryption, using a small tag allowlist. Scripts, images, SVG, style/class attributes and event handlers are removed. Only HTTPS link destinations and optional titles survive; sanitized links receive a separate target and noopener/noreferrer/no-referrer protections. Markdown uses the locally vendored marked parser and passes through the same sanitizer. Clipboard HTML is sanitized before insertion into the editor; HTML drag/drop is blocked. Fixed source-controlled SVG icons are inserted separately from user content. CSP blocks third-party scripts, inline JS, framing and arbitrary connections. Mutations require the exact configured `Origin` and JSON. The Edge Function allows CORS only for that origin; Vercel proxies requests under the same frontend origin. TLS/HSTS are required for public operation. No service worker, sessionStorage, IndexedDB, analytics, cookies or remote fonts are used. The only optional localStorage values are `whisper-theme` (`light`/`dark`) and `whisper-language`, written only after explicit appearance/language choices. No message content, link, PIN, key or seed is persisted there. If storage is blocked, appearance still works for the current page.

Single read uses database-atomic delete-returning. Other authenticated attempts cannot retrieve the same single-use ciphertext. A plaintext message already displayed stays on screen until closed or the page navigates away. This is deliberate. Page lifecycle handlers clear DOM fields and in-memory references; back/forward restoration shows a closed state. This is best-effort browser hygiene, not secure RAM erasure.

## What is not protected

- Anyone holding the complete link can attempt to read first. Share the code through a separate trusted channel when using a code.
- A malicious host can replace served JavaScript to steal keys. This web-delivered encryption model relies on the deployed frontend being trustworthy. This has not received an external security audit.
- Compromised devices/extensions, screenshots, copied text, browser sync/history, clipboard history, and previews containing the original shared URL are outside our control.
- SQL deletion is logical deletion. PostgreSQL WAL/replicas/backups, SQLite free pages, filesystem snapshots, logs at the hosting/proxy/provider layer and RAM may retain data. They retain ciphertext if the protocol is used correctly, but “zero trace” is not promised.
- Expiry rejects reads at the database predicate even before physical row cleanup. The local Rust backend sweeps every 30 seconds while alive; Supabase cron deletes at minute granularity independently of the Edge Function. Cloud verification is recorded in QA.md.
- Sender can lose a created link if the creation response is interrupted. A one-time message can be consumed if its open response is lost. These are unavoidable delivery tradeoffs in this simple design; no retry cache stores consumed ciphertext.
- The server knows approximate message size, expiry and request timing. Hosting providers can observe IPs/traffic metadata even without app logging.

## Abuse controls and production limits

The production Edge API keeps global request budgets in PostgreSQL (create/open/revoke 30/180/60 per minute, challenge 90 and metadata 180), shared across function instances. The database checks 10,000 active rows and 128 MiB aggregate ciphertext under a transaction advisory lock on creation. JSON bodies are capped at 2,850,000 bytes. Requests do not trust forwarded client-IP headers. An attacker can exhaust the shared budget; this is a small personal deployment, not a broadly public anonymous service.

No application request-body, credential, debug SQL-bind, analytics or replay logging is enabled. Hosting providers can retain traffic metadata independently. Review provider spend/storage controls before broader public use. A privileged service-role credential is used only inside the Edge Function; public database roles have no table/RPC access. The function exposes only validated operations through a SECURITY DEFINER RPC with an empty search path and service-role-only execution. The management deploy token is scoped to the dedicated Whisper project; per the owner's request it has no expiry and should be revoked/rotated when no longer needed. It is never sent to the frontend.

The alternative local Rust server retains process-local rate/challenge budgets and best-effort quotas; use one instance or add shared controls before self-hosting it at scale. Rotate the pepper knowing it makes existing PIN-protected messages unreadable. Never reuse an unrelated Supabase project.

## Optional rich text implementation

The formatting toolbar uses the browser's contenteditable/execCommand behavior (deprecated but still supported in the tested Chromium). Safari/Firefox/native iOS clipboard and rich editing have not been manually tested. Plain-text mode never downloads the sanitizer/editor modules. DOMPurify is vendored with its license in `web/vendor/`; update it by running `npm ci && npm run vendor:rich` and copying the package license again. Keep the vendored sanitizer current with upstream security releases.

## Gesture verification

Before message creation, POST `/api/challenges` with `{ "mobile": false }` (desktop) or `true` returns a cryptographically random ID, an unbiased desktop target from 1–100 (mobile target 100), and a 120-second lifetime. Create must include `verification: { id, answer }`. The server atomically removes the challenge on a verification attempt, checks the exact answer and requires at least 500ms elapsed. Replay, missing, wrong and expired challenges fail. Cancellation leaves a short-lived challenge row; no message secrets/content are attached. Production challenges store only hashed IDs and are consumed transactionally in PostgreSQL; a separate cron task removes stale challenges and budgets. The Rust local implementation holds them in process memory and supports one replica.

This is user-requested gesture friction, **not a strong CAPTCHA or proof of a human**. The target is public to the browser and an automated client can obtain it, wait and answer, or choose the mobile mode. The backend enforces lifecycle and request/storage budgets, not physical gesture authenticity. Use a dedicated human-verification provider/trusted-edge protection before exposing this as a broadly public service. No third party is contacted by the slider. Keyboard controls are available.

POST `/api/messages/{id}/metadata` requires the derived access capability and returns only expiry, single-read policy and whether a PIN is needed. It never returns ciphertext, consumes the record, or changes the PIN attempt budget. GET previews still never open messages.

## Voice and expanded text

Client text/rich limit: 262,144 UTF-8 bytes. Binary envelope limit: 2,097,152 bytes, including the encrypted audio MIME/duration/peaks header. The backend accepts ciphertext from 17 through 2,097,168 bytes (GCM tag included); The Edge JSON body cap is 2,850,000 bytes (Rust: 2,831,155) to accommodate base64 expansion and bounded fields. Production storage is guarded at 128 MiB of aggregate base64 ciphertext under a transaction lock; local Rust quotas are best effort under concurrency. No database schema change is needed.

MediaRecorder captures locally only after a deliberate hold and browser permission. AudioContext analyser supplies real amplitude values, not simulated speech. Hold release, pointer cancel, tab hiding, navigation and changing mode stop the tracks; stale permission results stop their own streams. Session generations prevent consecutive recording callbacks from mixing. Successful send, replacement, delete and page lifecycle cleanup revoke playback object URLs and release clip references. There is no microphone or speech-to-text service upload. CSP allows only blob media sources; Permissions-Policy grants microphone only to self, keeping camera and location denied.

After decryption, audio envelopes require an allowlisted audio MIME, finite duration up to 120 seconds, bounded integer waveform samples and nonempty body. Audio elements only receive a locally created blob URL. Existing text/rich/legacy links use the unchanged crypto namespaces and AAD. Browser codec availability varies; a recording is not promised to play on every browser/device. End-to-end encryption does not hide payload length or prevent recipients saving/recording playback. Memory clearing is best effort, not guaranteed physical erasure.

Clipboard auto-copy is a convenience, not secure sharing: the operating system or third-party clipboard history may retain the copied recipient capability. Only the share link is auto-copied; the PIN/revocation link stay separate. Clipboard refusal preserves the visible link and manual-copy control. No link history is added to browser storage.
